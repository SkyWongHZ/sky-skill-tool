# 八戒睡眠医院报告定制

用户只发禅道需求链接时，从读取需求开始。也接受能定位同一需求的明确编号。若输入只有链接、尚不能确定是否是医院报告定制，先读标题和正文确认范围，再执行本流程。

## 只读分析

以下协作 skill 按名称从已安装的 skill 列表加载。

1. 用 `zentao-cli` 读取禅道需求、相关子项和影响判断的附件，逐条提取目标机构及科室、报告类型、修改前后行为和验收范围。多子项分别判断，只纳入报告定制及其必要的上游能力。截图里的示例数据和旧会话里的操作授权不视为本次需求。CLI 无法读取正文或关键附件时，按 `chrome-use` 及本机浏览器约定使用已有会话只读查看。
2. 每次用 `lark-doc` 读取两份固定指南的最新相关内容，记录各自对本次需求的适用部分：
   - [睡眠定制报告模板修改指南](https://pcn2whemupak.feishu.cn/wiki/KjDDw4KxsiJiNRk68jncUPrznDh)
   - [机构报告评估建议定制操作指南](https://pcn2whemupak.feishu.cn/wiki/YQAYwXADGioFFTkM4iIc03Vpn8f)
3. 按 [项目核查指引](references/project-checks.md) 对照当前前端、后端和同类 `docs/`。从实际报告入口追踪模板、接口、生成、保存及输出路径。默认在现有授权连接上只读核查 `sleep_test` 与 `sleep_prod` 的相关配置和结构，按环境记录核查结果及日期。若涉及样例，先找合适的测试报告，只记录验收所需的信息。
4. 逐项标出**前端代码、后端代码、数据库配置或数据、数据库结构**是否需要改动，并附需求、代码位置或只读核查证据。测试样例准备和生产生效配置分别说清。链接或库不可访问时继续能做的部分，点明缺失证据及影响，相关结论标“待核实”；区分未查询、查询失败和查无记录。
5. 先给用户需求理解、改动判断、测试与生产差异、验收思路。只讨论会改变实现或验收的未决问题，例如固定展示是否回写、历史报告是否跟随最新版式、重推如何处理、已缓存的文件是否要重建。分析和讨论阶段不切分支，不改业务代码和数据库。

## 形成文档并衔接开发

- 需求明确后，检查工作区，核对远端生产分支的最新基线。在确有本次代码、SQL 文件或文档交付的仓库，从各自最新生产基线建独立的 `feature/...` 分支。根据仓库规则保护用户已有工作并复用合适的需求分支，不创建只用于查看代码的分支。
- 优先在前端仓库的项目 `docs/` 编写**一份**需求与验收 Markdown，沿用同类文档的命名和结构。用禅道来源及附件、适用机构/报告/模板、前后端与数据库影响、历史数据策略、验收场景和通过标准串起来。需要后端或数据库配合时写入同一文档并链接相应仓库/文件。用例写清测试前提、操作与预期，明确尚未执行的验证。
- 写好文档后等待用户表达同意实施。“开始做吧”“按文档实现”等明确的开发意图等同于“可以开发”；单独认可文档只确认需求。用户当次已经表达同意开发时，无需重复确认。
- 开发按已确认的文档和各仓库规则执行，后端沿用 `bjsm-cloud-code`，后续提测和发布按用户当次要求衔接 `merge-and-push`。

## 数据库改动须在执行前确认

- 测试和生产库默认只读。任何实际写入都要在执行前请用户确认，包括单份测试报告切模板、机构配置、结构迁移、回填，以及会间接写库的接口或任务。开发、提测或上线的同意不包含写库确认。
- 先做完只读核查，把**目标环境和库名、具体 SQL 或执行动作、涉及的表和记录、预计影响、执行后验证及可行的回退方式**发给用户审阅。等用户明确同意这份具体方案后再执行。测试与生产分别确认，测试库的同意不适用于生产库。
- 执行前重新核对目标环境和关键数据。若目标、语句或影响范围发生实质变化，更新方案后重新确认。执行后按方案回查实际影响并报告结果。
