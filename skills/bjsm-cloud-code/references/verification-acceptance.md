# 验证与需求验收

## 编译与静态检查

- 执行当前项目和模块规则要求的最小充分验证；不机械新增测试，也不跳过明确要求的检查。专项限制（包括 SNI）读取当前 `AGENTS.md`，不从历史会话推断。
- 按项目约定，完成代码后先编译和静态检查，通知用户启动服务，再进行真实接口联调；不要自动启动服务或用测试替代已要求的联调。
- 检查 `git diff --check`、完整相关差异与 `git status`，覆盖已暂存改动及相关新文件；复核调用方、权限、加密、金额、状态、SQL 和迁移/回滚影响。
- 证据对应当前代码。后续修改影响已有结论时补做相关检查；代码未变且无新疑点，不重复运行已通过检查。环境失败和未运行项如实记录。

## 真实接口联调

- 确认用户启动的服务包含本次代码、目标环境正确、必要 SQL 已执行；避免把旧服务或旧库误判为新实现问题。不能凭编译成功声称服务已更新。
- 按已确认验收项检查相关成功、失败、权限和数据变化；不只看 HTTP 状态，还核对业务返回及相关持久化/副作用。
- 按本次实际影响覆盖空值/清空、重复请求、异步回写、历史快照和共享入口等场景，不强制每个需求执行全部类别。
- 写入式联调遵守已授权环境与数据范围，不自行在生产制造测试数据；已有授权明确时直接执行，不重复确认。
- 服务未启动、环境不可用或必要条件缺失时，明确已验证和待验证部分及下一步；不能将条件未满足视为验收通过。

## 验收与完成说明

- 对照确认的业务标准逐项标记“已通过 / 未通过 / 待验证 / 待业务确认”，附足以支撑状态的证据。需求有歧义时回到业务确认；明确的实现偏差在授权范围内修复，再验证受影响项。
- 区分代码实现完成、编译通过、接口联调通过和业务验收完成。文件已改、SQL 无语法错误、接口返回成功都不能单独证明业务验收通过。
- 说明剩余缺口、实际影响和下一步；不以笼统的“建议进一步测试”代替具体待办。用户需要判断的业务结果保留待确认，不能替用户宣告已认可。
- 按项目规则新建或更新 `docs/需求进度/YYYYMMDD-需求简称.md`，记录范围、业务规则、修改文件、SQL/API/权限、验证、风险、待确认项和下一步。只读 review 遵守授权边界，不自行写文档。
- 文档反映最终实现，纠正已放弃方案和过期的文件、类名、配置或验证描述；需保留的历史明确标注。SQL 分别记清已编写、已检查、已在哪个环境执行。
- 完成说明突出实际行为变化、验证结果和未完成事项，避免堆砌命令记录。验收不等于已提交、合并或上线；只有请求交付时才进入 `$merge-and-push` 流程。
