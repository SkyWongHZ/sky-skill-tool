# 代码 Review

## 范围和基线

1. 遵守用户指定的单提交、多提交、分支或工作区范围，不擅自扩大为整仓审查。Review 默认只读，修复遵守主技能的授权边界。
2. 确认当前分支、HEAD、工作区及比较对象的来源。区分实际生产部署版本、目标分支最新版本和 Git 共同祖先；`merge-base` 用于分析分支分叉后的变化，不证明它就是线上版本。
3. 不默认把 `origin/master` 当作生产版本。核查可用的发布/部署记录、项目约定或用户明确提供的版本，说明证据；远端跟踪引用可能过期，不能仅凭名称宣称已核实线上状态。
4. 无法确认生产基线时写明缺口。可以在不违背用户范围的前提下使用明确标注的临时 Git 比较依据继续只读分析，但不能声称完成了相对实际生产的检查；若差异会决定结论，先澄清。
5. 分支整体 review 默认覆盖已提交、已暂存、未暂存和相关未跟踪文件。单提交 review 不自动把无关本地修改归入该提交；若其影响当前运行或行号，单独说明。
6. 区分本次需求、合并带入及其他本地工作。Git 祖先关系、文件树差异和实际部署状态是不同证据；提交很多或分支 ahead 不等于业务差异很多。

## 取得完整差异

先读最终差异和提交概览；范围漂移、可疑中间改动或用户要求时，再逐提交追溯。说明所用比较方式：

- 相对已确认版本的最终代码差异：使用该版本与当前提交/工作区的直接比较。
- 分支自身从共同祖先产生的改动：使用 merge-base/三点比较，并与目标分支后续变化区别开。
- 本地修改：分别检查 `git diff --cached` 和 `git diff`；用 `git status --short` 与 `git ls-files --others --exclude-standard` 查相关未跟踪文件并读取内容。普通 `git diff` 不包含未跟踪文件。

按需使用 `git diff --stat`、`--name-status`、`--check` 和 `-w` 辅助定位范围、空白噪声和格式问题，不能用忽略空白的结果替代完整差异检查。最终效果与分层差异结合看，避免只检查某一提交状态漏掉覆盖、撤销或冲突。

## 检查内容

- 沿请求接收 → 业务处理 → 数据库存取 → 返回前端追踪真实链路，覆盖相关 Controller、FORM/QUERY、Service、DAO、Mapper Interface/XML、DO、VO/DTO、SQL，以及影响结论的未改动调用方、映射和消费者。
- 应用主技能的需求边界、设计、复用、数据生命周期和 SQL 规则，及当前 `AGENTS.md` 的具体约束。优先业务正确与权限安全，再看可维护性、有证据的性能问题及风格。
- 检查新增文件职责、现有替代方案、放置位置和真实用途；检查共享工具、公共模块、全局配置、数据库和跨模块接口的必要性与消费者影响。
- 与已有需求/验收文档核对行为、文件、类名、配置和验证证据；没有文档时不能为了 review 凭空补需求或强制创建文档。
- 无关文件、生成内容、广泛格式化和纯空白差异应指出来源及处理建议；不要自动删除、恢复或暂存用户内容。
- 不凭 SQL 长、方法多、辅助类只有一个调用方或出现动态 SQL 就认定有缺陷。核查具体业务复杂度、输入信任来源、查询执行方式和边界；风格偏好不能包装为正确性问题。

## 报告与修复边界

按严重程度先报告可操作问题，每条给出当前代码位置、触发条件、证据、实际影响和建议方向。区分确定缺陷、待验证风险与风格建议，问题归属分为：

| 归属 | 处理原则 |
| --- | --- |
| 本次引入或扩大 | 本次需要处理的问题；修改仍遵守已有修复授权 |
| 历史遗留且未扩大 | 说明后不默认修改，不混入本次缺陷数量 |
| 本次依赖或加重的历史问题 | 解释关联、是否阻碍交付及最小必要修复 |
| 可选优化 | 不影响当前正确性，不作为交付阻碍 |

前后对比明确生产版本、分支中间版本和当前工作区，使用同一业务例子解释；行号以所指版本为准。必要时读取历史版本证明问题归属，不根据印象归类。

没有可操作问题时明确说明，并列出基线、环境或验证上的剩余缺口，不保证“绝对没有问题”。收到修复指令后处理已授权范围，并重新检查受影响结果；不要在只读 review 后静默修改。

讲解颗粒度和暂停方式遵循本次提示词，本流程不强制逐文件暂停。
